# Инфраструктура и деплой веб-приложения в Yandex Cloud

**Приложение доступно по адресу: https://rubinshtein.online**

Terraform создаёт инфраструктуру, Ansible разворачивает на ней приложение.

Приложение — блог на Fastify, упакованный в образ
[irubinshtein/devops-for-developers-project-74](https://hub.docker.com/r/irubinshtein/devops-for-developers-project-74).
Внутри контейнера оно слушает порт 8080 и при старте само прогоняет миграции
базы.

Развёрнуто в казахстанской инсталляции Yandex Cloud (регион `kz1`, зона
`kz1-a`).

## Состав инфраструктуры

| Ресурс | Назначение |
| --- | --- |
| `yandex_vpc_network` + `yandex_vpc_subnet` | Виртуальная сеть и подсеть `10.10.0.0/24` |
| `yandex_compute_instance` × 2 | Веб-серверы с Docker и контейнером приложения |
| `yandex_alb_load_balancer` | Балансировщик: HTTPS на 443, HTTP на 80 с редиректом |
| `yandex_vpc_address` | Статический публичный IP, на него смотрит домен |
| `yandex_cm_certificate` | Сертификат Let's Encrypt с автопродлением |
| `yandex_dns_zone` + `yandex_dns_recordset` × 3 | Зона домена, A-запись, www и запись для валидации |
| `yandex_mdb_postgresql_cluster` | База данных как сервис |
| `yandex_vpc_security_group` × 3 | Правила доступа: балансировщик, серверы, база |

Через cloud-init на машины попадает только SSH-ключ — всё остальное ставит
Ansible.

## Требования

- Terraform >= 1.6.3
- Ansible
- Python 3
- Аккаунт в Yandex Cloud с положительным балансом

## Подготовка облака

Выполняется один раз, вручную через консоль:

1. Создайте сервисный аккаунт и назначьте ему на каталог роли:

   | Роль | Зачем |
   | --- | --- |
   | `editor` | создавать сети, машины и кластер базы |
   | `storage.editor` | писать состояние в бакет |
   | `alb.editor` | создавать балансировщик |
   | `vpc.publicAdmin` | выделять публичные IP-адреса |
   | `certificate-manager.certificates.downloader` | читать сертификат для HTTPS |

   Роли назначаются со стороны каталога: **каталог → Права доступа**, а не в
   диалоге редактирования сервисного аккаунта.

2. Выпустите для него **авторизованный ключ** в формате JSON — им Terraform
   управляет ресурсами.
3. Выпустите **статический ключ доступа** — им бэкенд пишет состояние в бакет.
4. Создайте бакет в Object Storage и укажите его имя в
   [terraform/backend.tf](terraform/backend.tf).

Бакет создаётся руками, а не Terraform: он нужен уже на этапе `init`, до того
как Terraform получит возможность что-либо создавать.

Проверьте раздел «Квоты»: конфигурация создаёт отдельную облачную сеть, а лимит
на их количество в каталоге по умолчанию невелик. Если сети от прошлых проектов
не нужны, удалите их заранее.

## Настройка проекта

```bash
make setup
```

Команда собирает зашифрованный файл `ansible/vault.yml` (спросит
идентификаторы облака, каталога и ключи доступа) и инициализирует Terraform с
удалённым бэкендом.

Отдельно нужно добавить в хранилище пароль для базы данных:

```bash
echo "TF_VAR_pg_password: \"$(openssl rand -base64 24 | tr -d '/+=')\"" 
make vault-edit
```

Первая команда печатает готовую строку со случайным паролем — скопируйте её и
вставьте в файл, который откроется по второй команде.

## Работа с инфраструктурой

Перед любой командой Terraform загрузите секреты в текущую сессию терминала:

```bash
eval "$(./scripts/secrets.sh)"
```

Расшифровка спросит пароль от Vault. Переменные живут только в этом окне
терминала — в новой вкладке команду нужно повторить.

Дальше:

```bash
make plan      # показать, что будет создано
make apply     # создать инфраструктуру
make output    # адреса созданных ресурсов
make ssh       # подключиться к первому веб-серверу
make destroy   # удалить всё
```

Полный список команд — `make help`.

## Деплой приложения

Всё, что нужно Ansible, лежит в [ansible/](ansible/):

| Файл | Назначение |
| --- | --- |
| `playbook.yml` | Основной плейбук: подготовка серверов и деплой |
| `requirements.yml` | Внешние роли и коллекции |
| `inventory/terraform.sh` | Инвентарь, читающий адреса из Terraform |
| `group_vars/all.yml` | Несекретные переменные |
| `roles/app/` | Своя роль: запуск контейнера с приложением |
| `vault.yml` | Зашифрованные секреты |

Инвентарь не статический: скрипт вызывает `terraform output` и отдаёт Ansible
актуальные адреса машин и FQDN базы. Поэтому после каждого `apply` ничего
править руками не нужно — при пересоздании инфраструктуры новые адреса
подхватятся сами.

Порядок деплоя:

```bash
eval "$(./scripts/secrets.sh)"   # адреса читаются из стейта, нужны ключи
make galaxy                      # поставить внешние роли (один раз)
make inventory                   # посмотреть, что видит Ansible
make ping                        # проверить связь с серверами
make provision                   # поставить Docker
make deploy                      # выкатить приложение
```

Всё вместе, от пустого облака до работающего приложения:

```bash
make release
```

Плейбук разделён тегами: `setup` ставит Docker, `deploy` выкатывает контейнер,
`monitoring` настраивает агент Datadog. Поэтому при обновлении приложения
гонять подготовку заново не нужно — достаточно `make deploy`.

Деплой идёт по одному серверу за раз (`serial: 1`): пока обновляется первый,
второй продолжает обслуживать запросы, и балансировщик не остаётся без живых
бэкендов.

## Домен и HTTPS

Домен зарегистрирован у Namecheap и делегирован в Yandex Cloud DNS. У
регистратора указаны NS-серверы облака:

```
ns1.yandexcloud.kz
ns2.yandexcloud.kz
```

Всё остальное описано в [terraform/dns.tf](terraform/dns.tf): сама зона,
A-запись на статический адрес балансировщика и CNAME для `www`.

Сертификат выпускается автоматически. Terraform создаёт заявку в Let's
Encrypt, кладёт в зону запись `_acme-challenge`, дожидается проверки прав на
домен и передаёт готовый сертификат балансировщику:

```
yandex_cm_certificate.app        заявка, challenge_type = DNS_CNAME
yandex_dns_recordset.acme        подтверждающая запись
data.yandex_cm_certificate.app   ожидание выпуска (wait_validation)
```

Первый выпуск занимает несколько минут — `apply` в это время стоит на месте.
Продлевается сертификат сам, пока запись `_acme-challenge` остаётся в зоне.

Обращения по HTTP не теряются: на порту 80 у балансировщика стоит редирект на
HTTPS.

Смена домена — одна переменная:

```bash
make apply TF_VAR_domain_name=example.com
```

## Мониторинг

Агент Datadog ставится ролью `datadog.dd.agent`:

```bash
make monitoring
```

Агент запускает проверку `http_check` — раз в интервал стучится на
`http://127.0.0.1/` **своей же машины**. Это принципиально: проверка идёт мимо
балансировщика, поэтому видно состояние каждого сервера отдельно, а не только
сайта целиком.

Сам алерт описан в [terraform/monitoring.tf](terraform/monitoring.tf) и
создаётся вместе с инфраструктурой:

```bash
make apply
```

Монитор следит за сервис-чеком `http.can_connect`, сгруппированным по хостам.
Тревога поднимается после трёх неудачных проверок подряд, а через 10 минут
тишины от агента — отдельно, как «нет данных» (машина могла просто умереть).

Тег `service` связывает две половины: агент помечает им проверку
(`ansible/group_vars/all.yml`), а монитор по нему фильтрует
(`app_service_tag` в Terraform). Значения должны совпадать, иначе монитор
останется без данных.

Проверить работу можно, погасив контейнер на одной из машин:

```bash
make ssh
docker stop blog
```

Через минуту-две монитор перейдёт в `Alert`, а балансировщик выведет хост из
ротации — сайт продолжит отвечать со второй машины.

## Проверка результата

```bash
curl https://rubinshtein.online
```

Флаг `-k` не нужен — сертификат настоящий, выпущен Let's Encrypt.

До `make deploy` балансировщик будет отдавать ошибку — бэкендов ещё нет, на
машинах пусто. Это нормально.

## Стоимость

Инфраструктура платная и тарифицируется по времени работы. Веб-серверы по
умолчанию создаются прерываемыми (`web_preemptible = true`) — это существенно
дешевле, но облако вправе остановить их в любой момент и гарантированно
останавливает через 24 часа.

Не оставляйте стенд поднятым без надобности:

```bash
make destroy
```

## Секреты

Все секреты хранятся в `ansible/vault.yml`, зашифрованном через Ansible Vault,
и передаются снаружи — через переменные окружения. Ни в `.tf`-файлах, ни в
плейбуках нет ни одного значения ключа или пароля.

Одно хранилище обслуживает и Terraform, и Ansible: `scripts/secrets.sh`
расшифровывает его в переменные окружения, Terraform читает `TF_VAR_*`
автоматически, а плейбук берёт пароль базы через `lookup('env', ...)`. Поэтому
пароль от Vault спрашивается один раз за сессию, а не при каждой команде.

| Переменная | Назначение |
| --- | --- |
| `TF_VAR_yc_service_account_key` | Авторизованный ключ сервисного аккаунта |
| `TF_VAR_yc_cloud_id` | Идентификатор облака |
| `TF_VAR_yc_folder_id` | Идентификатор каталога |
| `TF_VAR_pg_password` | Пароль пользователя базы данных |
| `TF_VAR_datadog_api_key` | Ключ Datadog для отправки метрик агентом |
| `TF_VAR_datadog_app_key` | Ключ Datadog для управления мониторами через API |
| `AWS_ACCESS_KEY_ID` | Статический ключ для доступа к бакету с состоянием |
| `AWS_SECRET_ACCESS_KEY` | Секретная часть статического ключа |

Состояние инфраструктуры хранится удалённо, в Object Storage, и в репозиторий
не попадает.
